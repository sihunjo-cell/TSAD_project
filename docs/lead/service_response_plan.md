# 서비스 응답 범위 수정 계획

작성일: 2026-09-06

## 목적과 상태

후속 요청에서 튜닝 자체를 우선 수정하기로 범위를 좁혔다. 원본 후보 보존, 단일 진입 실행·재개,
model_ratio·tier_adaptive 근거 합집합을 코드에 반영했다. 현재 구현과 다음 실행 기준은
`plan_v5.md`와 `next_session.md`다. 아래 기업 조회·운영 범위 판정은 후속 설계로 남는다.

기업의 현재 정상 데이터와 확보계획을 받았을 때, 무엇을 답할 근거가 있고 무엇은 판단을 보류해야
하는지 정한다. 임의의 최대 행 수를 먼저 정하는 대신 실행 한계, 추천 근거 부족, 요구조건 위반을
구분한다. 이 문서는 후속 서비스 수정 계획이며 수치 상한의 검증 결과가 아니다.

현재 q별 모델·파라미터 선택과 전체 prefix 학습은 유지한다. 구현할 때의 기준 문서는 이 계획과
`plan_v5.md`이며, 서로 다른 현재 결정은 첫 작업에서 맞춘다. GHL·HAI 실행·평가 코드는 이번 수정
대상이 아니다. 로컬 테스트·구문 검사·모델 실행·원본 CSV 스캔 금지도 유지한다.

## 결정

튜닝은 후보와 관측 근거를 모으는 단계로 쓴다. 서비스 응답 범위는 그 근거와 별도 검증을 연결해
정한다. 튜닝 데이터의 최대 크기를 서비스 상한으로 바꾸거나, 선택에 사용한 점수로 선택된 설정의
기업 성능까지 인증하지 않는다.

| 접근 | 판단 |
| --- | --- |
| 튜닝에서 성공한 최대 크기를 상한으로 사용 | 후보 선정과 적용 범위 검증이 섞인다. 채택하지 않는다. |
| 튜닝 결과와 관계없이 별도 대규모 용량 실험 수행 | 기존 관측을 활용하지 못한다. 초기 수정 범위로 삼지 않는다. |
| 튜닝 근거를 재사용하고 필요한 범위만 독립 검증 | 채택한다. 추가 검증은 서비스가 실제로 답하려는 조건에 한정한다. |

공통 한도가 필요하면 업로드 크기·동시 작업 수 같은 운영 제한으로 명시한다. 모델 추천의 근거는
모델·config·head·실제 학습량·센서 수·처리량·실행 환경·평가 목적별로 관리한다. 서로 다른 파일의
행·열 최댓값을 합친 직사각형이나, 관측점 사이를 채운 연속 구간은 기본 지원 범위가 아니다.

## 기업에 반환할 판단

입력 오류나 필수 정보 누락은 보완할 항목을 안내한다. 데이터를 해석한 뒤의 판단은 세 가지로 둔다.

| 판단 | 필요한 근거 | 응답의 범위 |
| --- | --- | --- |
| 현재 조건 불충족 | 구조상 불가능하거나, 적용 가능한 검증 결과가 필수 조건 위반을 뒷받침함 | 어떤 모델·작업·현재/미래 지점에서 어떤 조건을 위반하는지 명시 |
| 판단 보류 | 미관측 규모·환경, 성능 근거 부족, 평가 자료 부족, 불확실한 충족 여부 | 부족한 근거와 그 근거가 필요한 주장만 보류 |
| 근거 범위 안에서 후보 제시 | 해당 주장을 뒷받침할 근거가 있고 필수 조건을 확인함 | 개발 근거이면 현장 검증 후보, 적합한 독립 근거가 있으면 그 조건 안의 비교 결과 |

판정은 모델별·현재/미래 지점별·주장별로 한다. 학습·추론 비용을 비교할 근거가 있어도 미탐 손실을
계산할 근거는 없을 수 있다. 한 후보의 실패 때문에 다른 후보까지 거절하지 않는다. 모든 후보를
충분히 확인하지 않았다면 “적합한 모델이 없다”고 단정하지 않는다.

관측 범위 밖이라는 사실은 실행 불가의 증거가 아니다. 통과를 입증하지 못한 경우와 실패를 확인한
경우를 구분한다. 성능 추정의 불확실성 때문에 합격을 확정하지 못하면 판단 보류다.

정상 데이터만 있는 기업에는 실행 가능성과 확인된 자원 근거를 설명할 수 있다. 정상 검증 자료로
오경보를 평가할 수는 있지만 미탐률은 확인하지 못한다. VUS-PR이나 정상 데이터의 분위수를 미탐률,
운영 오경보 보장 또는 오류 손실로 바꾸지 않는다.

## 근거를 확보할 위치

| 위치 | 확보할 근거 | 이 근거만으로 하지 않는 주장 |
| --- | --- | --- |
| 실행 전 정적 검사 | 스키마·세션·실제 prefix·window·patch·채널·후보 구조 조건 | 실행 가능성이 성능 충분성을 뜻한다고 하지 않음 |
| Dev18 q별 튜닝 | 모든 후보의 점수, 실제 n·d, 설정·head, 실행 성공·실패, 시간·메모리와 출처 | 신규 기업 성능, 연속적인 지원 영역, 서비스 부하 한도 인증 |
| 선택 후 자원 확인 | 고정 환경·처리 방식·부하에서의 학습·추론 시간과 메모리 | 처리 성공을 탐지 성능의 근거로 사용 |
| 별도 성능·추천 절차 평가 | 동결한 선택·응답 규칙의 적용 결과와 보류 여부 | 평가 결과를 보고 규칙을 고친 뒤 같은 자료를 독립 확인으로 재사용 |
| GHL·HAI 후속 인계 | 봉인된 후보의 외부 성능·재학습·추론 비용 근거 | 그 비용을 모든 신규 기업의 확정 비용으로 이전 |
| 현장 또는 적용 조건이 확인된 자료 | 운영 경보·미탐·지연과 기업 조건의 적합성 | 정상 미라벨 자료만으로 이상 탐지 성능 보장 |

GHL·HAI는 기존 외부 평가·비용 재측정 역할을 유지한다. 응답 규칙을 그 결과로 수정한다면 수정된
규칙에는 새로운 독립 확인이 필요하다. 이번에는 후속 담당자의 코드를 구현하거나 검사하지 않는다.

## 수정 작업 A — 현재 데이터와 확보계획 분리

대상: `src/common/select_conditional_policy.py`, `src/common/tuning_support.py`,
`tests/unit/test_conditional_policy.py`, `tests/unit/test_service_support.py`.

- [ ] 현재 후보 조회에서 기업의 계획량으로 q를 계산해 선택표를 고르는 경로를 제거한다.
- [ ] 현재 실제 학습량·센서 수·처리 조건에 맞는 관측 근거를 찾고, 각 근거의 개발 CSV·원래 N·q·집단을 보존한다.

- [ ] 미래 계획은 현재량부터 계획량까지 관측된 절대 데이터량 지점과 미확인 목표를 별도로 반환한다. 이 표는 비용 최적 경로가 아니다.

인수 사례: 현재 데이터·n·d·처리 조건을 유지하고 계획 N만 바꾸면 현재 후보의 근거는 유지된다.
미래 범위의 상태만 달라진다. 현재까지 검증됐지만 목표량은 미관측이면 현재 결과와 미래 보류를 함께
표시한다. 성장률이나 운영 기간이 없으면 대기시간·누적 비용은 계산하지 않는다.

## 검증 작업 — 범위를 넓히기 전에 확보할 근거

코드 수정의 회귀 검증과 서비스 범위의 실증 검증은 서로 다른 완료 조건이다. 전자는 실행 허용 후
관련 순수·모킹 검사만 수행한다. 후자는 원격 환경에서 다음 계약을 먼저 봉인한 뒤 진행한다.

자원 확인은 기존 사전 자원 검사를 출발점으로 사용하되, 후보별 대표 한 건 통과를 서비스 용량
검증으로 승격하지 않는다. 모델·설정·센서 수·장비·dtype·전처리·학습/추론·배치·동시 실행·유입량과
허용 시간을 고정한다. 튜닝 관측에 가까운 필요한 경계 지점부터 확인하며, 부족한 범위만 추가한다.
합성 확장이나 반복 데이터는 계산 부하 확인에만 쓰고 성능 근거에서 제외한다. 연속 범위를 허용하려면
중간 지점과 최악 조건을 포함한 근거가 필요하다. 성공한 최대 지점 하나로 그 이하 전부를 승인하지 않는다.

성능·추천 절차의 검증은 허용할 오류, 응답 범위, 자료 분리와 평가 단위를 먼저 정한다. 범위나 기준을
결정하는 자료와 최종 확인 자료를 분리한다. q별 모델·설정 선택까지 포함한 전체 절차를 동결해 평가하고,
시계열의 각 행이나 같은 실행의 seed를 독립 기업 사례처럼 세지 않는다.

확인할 결과는 답한 사례의 요구조건 위반 정도, 답할 수 있었던 범위, 보류 사유별 건수다. 모두 보류하면
위반을 피할 수 있으므로 보류율도 함께 보고한다. 근거가 너무 적거나 적용 조건이 다르면 숫자 보장 대신
미검증으로 남긴다. 데이터셋 단위 평가와 현장 단위 성능 보장은 구분한다.

GHL·HAI에서는 동결한 후보의 비용을 해당 데이터·환경에서 다시 측정한 값으로 인계받는다. 공통 HPO
개발비를 기업마다 반복 부과하지 않는다. 현재 작업은 인계 계약까지이며 측정 코드·운영 threshold·최종
비용 최적화 구현은 포함하지 않는다. 알려지지 않은 기업의 부하·발생 빈도·손실 단가를 벤치마크 값으로
자동 대체하지 않는다.

## 완료 기준과 범위 확대

이번 수정의 완료 기준은 응답 사유를 근거에 연결하고, 현재 데이터와 미래 계획을 분리하며, 선택된
후보의 근거를 잃지 않는 것이다. 수치 상한 인증이나 새 기업 성능 보장 완료가 아니다.

검증 범위를 넓히는 작업은 실제로 보류되는 요청과 그 원인을 보고 정한다. 처음부터 추천 영역 학습기,
성능 외삽 모형, conformal 보장, 기업별 자동 HPO를 추가하지 않는다. 해당 기능의 필요성과 별도
검증 자료가 확보됐을 때만 독립 과제로 다룬다.

첫 구현 작업은 A와 그 회귀 계약이다. 완료 보고 뒤 B, C, D 순서로 진행하며 저장소의 현재 게이트
규율을 유지한다. 기존 결과와 미완료 실행을 삭제하지 않고, 후보나 실행 신원이 바뀌면 새 예산으로 봉인한다.

## 선행연구에서 가져오는 범위

[TSB-AD 공식 튜닝 코드](https://github.com/TheDatumOrg/TSB-AD/blob/e0975a5f7d3e65ab77e9fab24d1b5b51acda8f48/benchmark_exp/HP_Tuning_M.py)는
CSV와 파라미터 조합을 순회해 평가한다. 현재 연구는 이 후보 평가 절차에 q별 선택을 추가한다.
튜닝 파일의 최대 행 수를 서비스 한도로 정하는 절차를 가져온 것은 아니다.

[LCDB 1.1의 학습량 구성](https://github.com/learning-curve-research/LCDB-1.1/blob/4676ddcc41818ad978fb081e73e65257ff398982/experiments/jobs_create.ipynb)은
확보한 학습량 안의 지점을 사용한다.
[TimeEval의 실행 제한](https://github.com/TimeEval/TimeEval/blob/d0a9187a34765fba4ebdd5ac2b523b5685edb3b2/timeeval/adapters/docker.py)은
메모리와 시간을 실행 조건으로 명시한다. 둘 다 실험 범위와 자원 제한의 근거이며 신규 기업의 성능을
인증하는 절차는 아니다.

ICLR 2024 Conformal Risk Control의
[공식 실험 코드](https://github.com/aangelopoulos/conformal-risk/blob/3eff946390a8f188b1e5ab700fce21a66a215e7c/polyps/risk_histogram.py)는
교정 자료의 손실로 기준을 정하고 분리한 validation 자료에서 위험을 평가한다. 이 계획은 그 역할
분리를 참고한다. CRC 알고리즘을 도입하거나 교환 가능성·유계·단조 손실 등의 조건이 확인되지 않은
TSAD에 통계적 보장을 붙이지 않는다. 특히 수락한 기업 추천의 실패율을 자동으로 보장하지 않는다.
